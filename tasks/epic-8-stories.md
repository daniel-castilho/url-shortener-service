| **8.1** | **Contrato de release** – escrever como o código validado vira produção, e registrar as decisões que o Épico 8 toma (e as rejeitadas). | • `docs/release-engineering.md` com o fluxo completo: tag anotada `vX.Y.Z` → gates da `release.yml` (nunca pulados) → GitHub Release (jar do build da CI + sha256 + SBOM + notas) → `scripts/deploy.sh <tag>` no host → post-deploy verification. Colunas equivalentes da matriz: etapa, quem executa (CI × operador), o que falha, o que acontece (fail-closed). <br>• ADR 0007: blue-green em bare metal — duas unidades concretas blue (:8080) / green (:8081) com **jar por cor** (o template atual usa jar único compartilhado, o que impede artifact por cor); template nginx é fonte única, `deploy/runtime/nginx.conf` é **renderizado** (nunca commitado, nunca mutado pelo tooling); cutover fail-closed: qualquer pré-condição/passo falha → aborta para a cor antiga a 100%, nova cor drenada e parada, exit não-zero com o passo nomeado; canary 10/30/100, dwell 30s, smoke após cada bump; `deploy/runtime/last-deploy.txt` (previous/current/tag/at). Consequência aceita: pós-cutover a frota = 1 ativa + 1 idle (capacidade 1×; capacidade 2× exige instância extra fora do plano de deploy — escrito). <br>• ADR 0008: promoção de artifact — o jar **construído pela gates job** é o promovido (single build, asset do Release, sha256 registrado); `deploy.sh` baixa o jar exato da Release (nunca rebuild local); imagem Docker é artifact secundário (non-root + Trivy HIGH/CRITICAL + CycloneDX SBOM); tag imutável (fix-forward `vX.Y.Z+1`, nunca mover tag); GITHUB_TOKEN only. Rejeitados: SSH-deploy da CI, registry como caminho obrigatório, `mvn release:perform`. <br>• `git log --oneline -- docs/adr/ docs/release-engineering.md` colado no DoD. | Padrão ADR (Nygard); `docs/release-runbook.md` §12; dargent `scripts/deploy.sh` (padrão de referência, repo do próprio owner) |
| **8.2** | **Identidade do artifact** — jar e imagem carregam a semver da tag; tag com CHANGELOG sujo não sai. | • pom: propriedade `revision` (`0.0.1-SNAPSHOT` local) + `flatten-maven-plugin` (modo `resolveCiFriendliesOnly`); release roda `./mvnw -B clean package -DskipTests -Drevision=<semver>` → `target/url-shortener-service-<semver>.jar`. Evidência: `./mvnw -q help:evaluate -Dexpression=project.version -Drevision=0.14.0` imprime `0.14.0` **e** o nome do jar do package; `./mvnw verify` verde com o padrão (nenhum gate quebrado pelo flatten). <br>• Dockerfile: `ARG VERSION` + `LABEL org.opencontainers.image.version` (não muda o build atual; consumido pela release job). <br>• Gate CHANGELOG na `release.yml`: falha se a seção `## [Unreleased]` do `CHANGELOG.md` no commit da tag estiver ausente ou com entries (regra keep-a-changelog: Unreleased é promovido na tag, nunca tag com rascunho). Teste do gate colado (run verde + run propositalmente vermelho em branch descartável). <br>• Nome do artefato no Release segue a tag; `deploy.sh <tag>` resolve o jar por semver, não por "último build". | `pom.xml`, `Dockerfile`, `CHANGELOG.md` (keep a changelog já em uso) |
| **8.3** | **Blue-green com canary fail-closed** — `deploy.sh` troca a versão em produção sem downtime e aborta de volta em qualquer falha. | • Units concretas `deploy/url-shortener-blue.service` (:8080, jar `/opt/url-shortener/blue/url-shortener.jar`) e `deploy/url-shortener-green.service` (:8081, jar `/opt/url-shortener/green/url-shortener.jar`), com o mesmo hardening do template (`NoNewPrivileges`, `ProtectSystem=strict`, `KillMode=mixed`, SIGTERM, `TimeoutStopSec=30`, `Type=notify`); o template `url-shortener@.service` **permanece** para scale-out ≥3 instâncias (runbook §12) — plano de deploy = blue+green apenas. <br>• `scripts/deploy.sh <tag>`: baixa o jar da Release (verificação sha256 contra o asset publicado) → estagia e sobe/reinicia a cor idle com o novo jar (graceful) → wait de readiness em `:<porta>/actuator/health/readiness` com **budget nomeado** (`READY_BUDGET_SECONDS=90` — justificado no script: HEALTHCHECK do Dockerfile usa start-period 40s; 90 = margem para boot prod + migrator fail-fast) → render do runtime conf (peso green 10/30/100, blue o complemento) → `nginx -t` **antes** de `nginx -s reload` em cada bump → `scripts/smoke.sh` após cada bump → dwell 30s → sucesso: grava `last-deploy.txt`, drena e para a cor antiga, one-liner. <br>• **Fail-closed:** qualquer pré-condição ou passo falha → render da cor antiga a 100% + reload + dreno/parada da cor nova + exit ≠ 0 com o passo ofensor nomeado. O template `deploy/proxy/nginx.conf` nunca é mutado pelo script (fonte única humana); `deploy/runtime/` vai para `.gitignore`. <br>• Upstream do template normalizado para **duas linhas ativas** (blue+green, weight 100/100) — hoje a linha 8081 está comentada; o render substitui as duas linhas. <br>• Modos testáveis sem tocar produção: `--check <tag>` (imprime plano + última deploy, não muta nada), `--init` (renderiza runtime conf blue 100 / green down), `--active` (imprime cor ativa), `--self-test` (render + asserções de peso em dir temporário + prova do abort fail-closed com readiness morto: `READY_BUDGET_SECONDS=1` contra porta morta → aborta para a cor antiga). Output do self-test colado. | `deploy/proxy/nginx.conf` (upstream atual), `deploy/url-shortener@.service`, dargent `scripts/deploy.sh` (referência de arquitetura: render por awk, `--check`/`--init`/`--active`, `last-deploy.txt`) |
| **8.4** | **Smoke de runtime + rollback de linha** — uma sonda prova que o stack está servindo; uma linha desfaz o deploy. | • `scripts/smoke.sh <base>`: pernas sequenciais, exit ≠ 0 **nomeando a perna falhada**: (1) `GET /actuator/health/liveness` → 200; (2) `GET /actuator/health/readiness` → 200; (3) `GET /actuator/info` → 200; (4) `POST /api/v1/urls` (anônimo, `originalUrl` único por run) → **200** + corpo com `id` e `shortUrl` + header `X-Request-Id`; (5) `GET /<id>` (sem follow) → **302** + `Location` == `originalUrl`; (6) `HEAD /<id>` → 302 (HEAD espelha GET — fix do EP7, `ReadPathIT#headMirrorsGetOnRedirectPath`); (7) `GET /zzzzzzz` (7 chars Base62 válidos) → **404**; (8) `POST /api/v1/urls` com `ttlSeconds: 1` → 200 + `id2`; poll `GET /<id2>` até **410** (budget 15s — expiry é verificado eager na aplicação, o cache nunca serve expirado). <br>• **Dois consumidores:** deploy.sh (após cada bump, contra a frente nginx) e CI (job `runtime-smoke` na `release.yml` — compose/services mongo+redis + jar da tag + `smoke.sh` + `verify-graceful-shutdown.sh` como última perna: zero connection-refused durante o dreno). Contratos lidos do código (`ShortenResponse{id, shortUrl}`, status 200 do `@ApiResponse`, `RequestCorrelationFilter` echoing `X-Request-Id`) — colados no DoD, não inventados. <br>• `scripts/rollback.sh`: lê `deploy/runtime/last-deploy.txt` (previous/current/tag/at) → `systemctl start` da cor anterior (o jar dela **não foi tocado** — cutover parou, não apagou) → render (anterior 100 / atual down) → `nginx -t` + reload → smoke → one-liner de incidente (`rollback blue→green reverted to blue at <iso> (deploy <TAG> cut over, panicked)`). Sem rebuild. `--self-test` (last-deploy sintético → asserções do render). <br>• Runbook §2 passa a documentar o `rollback.sh` (o procedimento manual vira fallback nomeado). | `scripts/smoke.sh` (novo), `scripts/rollback.sh` (novo), `scripts/verify-graceful-shutdown.sh` (EP7), dargent `scripts/smoke.sh`/`rollback.sh` (padrão de referência) |
| **8.5** | **Backup agendado, manifestado e verificado** — o backup roda sozinho e o restore é um contrato que falha. | • `deploy/systemd/url-shortener-backup.service` (`Type=oneshot`, usuário dedicado, `After=docker.service`) + `.timer` (`OnCalendar=*-*-* 03:30:00` local — **depois** do retention purge 02:00 UTC e do rollup 01:10 UTC, racional no comentário; `Persistent=true` para pegar corrida perdida — padrão dargent `dargent-backup.timer`). <br>• `scripts/backup-mongodb.sh` ganha **manifest** (`manifest.json` ao lado do dump): timestamp, db, mongodb version, tamanho, e **row counts por collection** (`short_urls`, `users`, `custom_domains`, `click_events`, `click_daily`, `schema_migrations`) — lidos via `mongosh` (mesmo requisito de tools em PATH do EP7, com fallback `docker exec` documentado como no drill do EP7). A rotação de 30d existente permanece. <br>• `scripts/restore-mongodb.sh --verify <dir>`: restore + re-conta as mesmas collections + compara com o manifest + **exit ≠ 0 em qualquer divergência** (tabela colada). Contrato: *"backup sem restore verificado é esperança"* (dargent E14 — mesmo padrão, mesmo owner). <br>• `scripts/ci-restore-drill.sh` (corpo do job `restore-drill` da `release.yml`, executável local): projeto compose **isolado** (`urlshortener-drill`, portas 18xxx — padrão EP5/6/7: nunca toca o stack de dev), seed 20 códigos via API + 2 códigos pós-backup, `backup-mongodb.sh` → drop `short_urls` → `restore-mongodb.sh --verify` → asserts: seeds pré-backup = **302**, seeds pós-backup = **404** (RPO = último backup, semântica do drill EP7) + **RTO medido** (wall-clock do backup→restore→verify) ≤ `RTO_BUDGET_S=300`; manifests/subidos como artifact (o registro é o deliverable). <br>• Failover de alerta de backup: **fora de escopo** (não existe aggregator/agent no topo atual) — o runbook pré-release inclui `ls -lt /var/backups/url-shortener | head -1` (backup com < 26h) e o drill de release é a garantia forte; vira TD item, não gap silencioso. | `scripts/backup-mongodb.sh`, `scripts/restore-mongodb.sh`, `docker-compose.yaml`, dargent `deploy/systemd/dargent-backup.{service,timer}` + `scripts/ci-restore-drill.sh` (padrão de referência) |
| **8.6** | **Release como gate** — tag `v*` só vira Release se passar em tudo; o runbook reflete o fluxo novo. | • `.github/workflows/release.yml` (trigger **apenas** tag `v*`; `permissions: contents: read` no top-level, `write` só no job `release`): <br> 1. job `gates` — checkout `fetch-depth: 0`; `./mvnw -B verify -Drevision=<semver>` (unit+IT+JaCoCo+SpotBugs+Spotless+OWASP no verify); gates bash (`check-boundaries`, `check-security`, `check-metrics-frozen`, `check-doc-sync` + self-tests); promtool check/test + amtool check-config (mesmas pinned do CI atual); **gate CHANGELOG** (Unreleased vazio/ausente → fail); monta o jar da release e faz `upload-artifact` (é **este** jar que o `release` promove — single build). <br> 2. job `k6-gate` (needs: gates) — services mongo+redis (mesmo padrão da `load-test.yml`), app com rate limits relaxados, `k6 run load-tests/mixed.js` (~2m, rps nominais) — **o exit do k6 já é o gate** (thresholds `p95 < 200ms`, `http_req_failed < 0.1%` já estão nos scripts); artifact k6 sempre. <br> 3. job `runtime-smoke` (needs: gates) — baixa o jar do artifact, sobe app + services, `scripts/smoke.sh`, depois `scripts/verify-graceful-shutdown.sh` (dreno sem connection-refused — EP7 de volta à porta do release); logs em falha. <br> 4. job `restore-drill` (needs: gates) — `scripts/ci-restore-drill.sh` (story 8.5); artifact dos manifests + RTO. <br> 5. job `release` (needs: gates, k6-gate, runtime-smoke, restore-drill) — resolve semver da tag; `docker build` da imagem + **non-root gate** (`docker run --entrypoint id` → falha em UID 0) + **Trivy HIGH/CRITICAL** (action SHA-pinned) + **SBOM CycloneDX** da imagem; baixa o jar do artifact da `gates`; `sha256sum`; `gh release create` com jar + `SHA256SUMS` + SBOM + notas (anotação da tag + `--generate-notes`). GITHUB_TOKEN only. <br>• `docs/release-runbook.md`: §1 reescrito (deploy = `scripts/deploy.sh <tag>` + post-deploy verification: smoke + vigilância de burn-rate 10 min no SLO dashboard + checagem de `schema.migrations.*` nos logs), §2 = `scripts/rollback.sh` (manual vira fallback), §7 checklist pré-release acrescido de: tag anotada; Unreleased vazio; **migrations desde o tag de `last-deploy.txt` são expand-only** (review do diff dos `V*` — o migrator é fail-fast, mas migração destrutiva quebra o blue antigo no cutover); backup com < 26h; drill verde na release (link do workflow). Nova seção "Release artifacts & promotion" + incidente "deploy falhou" (one-liner + rollback). <br>• No fechamento: item novo na matriz de debt do `AGENTS.md` (EP8) + linha Deployable no README Current State; `check-doc-sync` verde. | `.github/workflows/ci.yml` (padrão dos jobs), `.github/workflows/load-test.yml` (padrão k6), dargent `.github/workflows/release.yml` (padrão de referência), `docs/release-runbook.md` |
