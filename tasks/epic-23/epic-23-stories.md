# Epic 23 — Stories and Acceptance Criteria

| # | Story | Acceptance criteria | Primary references |
|---|---|---|---|
| **23.1** | **Define a reviewable documentation-impact map** — contributors can see which documents are expected to change for high-impact source areas. | • Add a structured map with stable rule IDs, source globs, and documentation target groups for API, configuration, persistence, and release-process changes. <br>• Verify every source glob and target against the current repository tree; do not leave example paths in the active map. <br>• Support a precise target contract (all required groups or at least one path from a declared alternatives group). <br>• Validate the map itself: required fields, unique rule IDs, non-empty patterns, existing target paths or explicitly allowed new-document paths, and coverage of every declared in-scope source root. <br>• Print the matching rule IDs and expected document targets in CI output. <br>• A new high-impact source root cannot become silently untracked; map coverage changes require review. | `docs/documentation-impact-map.yml` (or agreed format); `AGENTS.md`; repository path inventory. |
| **23.2** | **Gate changed paths against expected documentation** — related code and documentation changes stay together, while legitimate no-impact changes remain explainable. | • Implement a deterministic checker such as `scripts/check-doc-impact.sh` with explicit `--base` and `--head` inputs; no reliance on the developer's working tree or an implicit `HEAD~1`. <br>• Detect changed source paths for each map rule and compare them with the rule's documentation target groups. <br>• Pass when required documentation paths are changed. Fail when required documentation is absent and no valid no-impact rationale exists. <br>• Accept a well-formed `Docs-Impact: none - <specific reason>` from the supported PR-body or commit-trailer source; report it as an exception for human review, never as documentation updated. <br>• Reject an empty, generic, malformed, or whitespace-only rationale. <br>• Handle merge-base, zero/initial push, deleted/renamed files, paths with spaces, docs-only changes, and files matched by multiple rules deterministically. <br>• Do not impose a PR-only workflow or treat a no-impact declaration as owner approval. | `scripts/check-doc-impact.sh`; CI event payload; commit-message trailer contract. |
| **23.3** | **Integrate a self-testing gate into CI** — the policy is enforced consistently and its own blind spots are tested. | • Run the checker on both supported PR and push events with the correct base/head range. <br>• Add `--self-test` following the repository's existing gate pattern. <br>• Self-tests prove: (a) mapped source change without docs/rationale fails; (b) mapped source change with an allowed doc target passes; (c) valid no-impact rationale is surfaced; (d) invalid rationale fails; (e) docs-only/unmapped non-target change behaves as specified; (f) every required source root remains covered by the map. <br>• The CI step is required for successful CI; it is not `continue-on-error`, advisory, or silently skipped. <br>• Preserve `check-doc-sync.sh`, living-spec, release-evidence, boundary, security, metrics, and other existing gates. | `.github/workflows/ci.yml`; `scripts/check-doc-impact.sh --self-test`; existing CI conventions. |
| **23.4** | **Document the contributor contract and limits** — authors and reviewers know how to keep documents synchronized without overstating automation. | • Update `AGENTS.md` with the new change-impact rule, supported no-impact declaration syntax, and the fact that a rationale is reviewable but not automatic approval. <br>• Update relevant contributor documentation with the mapping categories and how to run the checker locally. <br>• Keep `docs/documentation-impact-map.yml` as the authoritative mapping; do not duplicate its rules in multiple prose lists. <br>• Update `CHANGELOG.md` as required and keep existing doc-sync checks green. <br>• State explicitly that a passing path gate proves required paths/rationales were present, not that prose is semantically accurate. <br>• Keep the policy repository-specific and in English; do not change frontend contributor rules. | `AGENTS.md`; `docs/`; `CHANGELOG.md`; `scripts/check-doc-sync.sh`. |

## Story dependencies

```text
23.1 impact-map contract
  → 23.2 changed-path checker
    → 23.3 CI integration + self-tests
      → 23.4 contributor documentation and closure
```

The checker and CI wiring depend on a verified map. Documentation policy must describe implemented behavior, not aspirational behavior.
