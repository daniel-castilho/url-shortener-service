# Epic 22 — Stories and Acceptance Criteria

| # | Story | Acceptance criteria | Primary references |
|---|---|---|---|
| **22.1** | **Define and generate one canonical release-evidence record** — an operator can identify the exact release inputs and outcomes without transcribing facts by hand. | • Define and version a JSON schema for `RELEASE-EVIDENCE.json`; reject unknown/missing required values and malformed hashes/URLs. <br>• Record repository, tag, semantic version, annotated-tag object type, resolved source commit, originating workflow/run/attempt/number/URL, event, authoritative final conclusion and completion time, required job conclusions, candidate JAR name/SHA-256, image identity, image-embedded JAR SHA-256, SBOM filename/SHA-256/subject, and the published assets' names and SHA-256 values where applicable. <br>• Populate fields only from the originating run's context, verified files, GitHub API, or verified Release assets. Do not parse manually authored prose as the source of truth. <br>• Generate `RELEASE-EVIDENCE.md` and any Release-body summary from the JSON; do not edit the rendered copy independently. <br>• Use UTC with an explicit `Z` suffix. The final run conclusion/completion time must come from GitHub after the original run is complete. If unavailable, fail closed or omit it with an explicit reason; never substitute the generator's time. <br>• Do not put the report's own digest inside itself. | Epic 21 provenance contract; GitHub Actions run/job/API outputs; Dargent `docs/handoff-dod.md` zero-from-memory principle (adapted, not copied wholesale). |
| **22.2** | **Capture same-run receipts and cross-check artifact identity** — every consumer proves which candidate bytes it received and used. | • The build job emits a candidate receipt containing the repository, tag, source commit, run ID/attempt, JAR filename, and observed SHA-256. <br>• Each required candidate consumer (k6, runtime smoke, restore drill, and release packaging) emits a receipt with the same identity fields and the hash it verified immediately before use. <br>• Receipts are uploaded under the originating run and retrieved only by its exact run ID/attempt; no latest-run lookup or fallback is allowed. <br>• The finalizer rejects missing, duplicate, stale, malformed, or cross-run receipts and any candidate SHA disagreement. <br>• The Release JAR downloaded through GitHub is hashed and compared with the candidate receipt and `SHA256SUMS`. <br>• If an image is built, the hash of its extracted JAR equals the candidate JAR hash, and the SBOM subject identifies that same verified image. <br>• All required release gates must have successful conclusions in the originating run. A failed, skipped, cancelled, or missing required job blocks publication. | `.github/workflows/release.yml`; `scripts/verify-release-artifact.sh`; candidate provenance and checksum; SBOM parser/contract. |
| **22.3** | **Finalize evidence after the run and publish fail-closed** — the published Release contains evidence about the completed run and its actual assets. | • The normal release job creates or updates only a **draft** Release after its required dependencies succeed; it does not make the release public before final evidence validation. <br>• A narrowly scoped post-run finalizer processes only the expected release workflow in the same repository and only a completed run with the expected event/tag and successful conclusion. It must reject untrusted or unrelated `workflow_run` events. <br>• The finalizer retrieves the exact originating run, attempt, job conclusions, receipts, and draft Release by run ID/tag; it does not use the finalizer run's SHA or attempt as the release identity. <br>• It verifies that the current annotated tag resolves to the originating source commit, then verifies the actual draft Release assets and all cross-asset identities before generating the final report. <br>• It attaches `RELEASE-EVIDENCE.json` and the generated human-readable report, then publishes the draft only after all checks pass. Any error leaves the release unpublished and reports the precise failed check. <br>• Set least-privilege permissions (`actions: read`; `contents: write` only where required). Do not expose write-capable credentials to pull-request code. <br>• The report states observed current tag object type/target. It does not claim to prove historical immutability. Tag update/deletion prevention remains dependent on separately verified GitHub repository controls. | `.github/workflows/release.yml`; new post-run workflow or equivalent; GitHub Release API; repository tag-protection disposition. |
| **22.4** | **Make the release record auditable without manual duplication** — maintainers can close an epic or release review by citing stable generated evidence. | • Update `docs/release-runbook.md` to describe the draft → finalizer → publish sequence, evidence fields, failure behavior, and how to retrieve the report. <br>• Update the appropriate DoD template or Epic 22 DoD instructions to require the exact report asset and originating run URL; stop manually copying per-release hashes, timestamps, image IDs, or job outcomes into narrative text. <br>• Keep historical Epic 21 disposition intact; do not change the recorded waivers into passed criteria or alter `v0.15.0`. <br>• Update `CHANGELOG.md` and any directly affected repository documentation according to `AGENTS.md`. <br>• Add a testable traceability row: requirement → implementation/gate → test → generated evidence. <br>• Do not claim GitHub tag-protection settings are enabled unless an owner has independently verified the actual repository settings. | `docs/release-runbook.md`; `AGENTS.md`; `CHANGELOG.md`; Epic 22 DoD. |

## Story dependencies

```text
22.1 schema and deterministic generator
  → 22.2 same-run gate receipts and cross-artifact checks
    → 22.3 post-run finalization and draft publication
      → 22.4 runbook, DoD, CHANGELOG, and evidence closure
```

Story 22.3 depends on the schema and receipts from 22.1–22.2. The GitHub tag-protection ruleset is an external prerequisite for future releases, not something this epic may claim to have configured by editing repository documentation.
